# Flower-Battle Presenter Visual-Regression Baselines (WP-PRESENTER-8)

This directory stores one baseline file per `(fixture, viewport)` pair —
**55 files total** (11 Pflicht-Fixtures × 5 Viewports). Each file is a JSON
document generated by `visualRegression.test.tsx`:

```json
{
  "hash": "abc123def456",
  "measurements": {
    "plantHeightsPx": [100, 100],
    "visiblePlotCount": 2,
    "cloudCount": 2
  },
  "fixtureTitle": "2 Teams Stage 1",
  "viewportLabel": "Beamer Default",
  "updatedAt": "2026-07-31T13:55:00.000Z"
}
```

- `hash` — 64-bit FNV-1a digest of the canonicalised presenter-mock markup
  (sky band + plant divs + team meters + event banner + real
  `FlowerBattlePresenterHud` output). Binary: any visual change flips it.
- `measurements` — derived plant heights, visible plot count, cloud count.
  Used for the human-readable diagnostic when the hash diverges.

## False-PASS-Schutz (SDD §11.3)

Every regression test runs **before** the hash comparison:

- Plant count matches fixture team count
- Team-meter count matches fixture team count
- Sky band present (non-empty canvas)
- Event-banner (when present) includes team + power-up names
- Reduced-motion flag honoured when fixture sets it

A fixture that fails any of these throws with the missing signals,
before the hash comparison ever runs.

## How to Update a Baseline

Baselines are **owner-gated**. The test runner fails with a clear
diagnostic if the markup hash drifts:

```text
[visual-regression] 2teams-stage-1 @ 1366x768
  baseline hash: cbf29ce484222325 (updated 2026-07-31T13:55:00Z)
  current  hash: deadbeef00112233
  measurements delta:
    plantHeightsPx: 100,100 -> 100,110
    visiblePlotCount: 2 -> 2
    cloudCount: 2 -> 2
  markup excerpt: <!doctype html>…
To refresh after deliberate visual change:
  OWNER_APPROVE_VISUAL_BASELINE_UPDATE=1 pnpm --filter @razzoozle/web test visualRegression
```

**Workflow:**

1. Review the diagnostic + the markup excerpt.
2. If the change is intentional, run:
   ```bash
   OWNER_APPROVE_VISUAL_BASELINE_UPDATE=1 pnpm --filter @razzoozle/web test visualRegression
   ```
   This rewrites every divergent baseline in-place.
3. Commit the updated `*.json` files in the same PR as the visual change.
4. Do **not** raise the tolerance (there is none — the hash is binary) and
   do **not** silently update baselines without the env token.

## Performance-Verschlechterung > 20 %

The benchmark harness in `__tests__/perf/` (W9-7) measures the
FlowerBattleCanvasHost's mount / update cost. A visual-regression change
that slows the procedural Pixi scene by more than 20 % must be justified
in the PR description with one of:

- A new overlay type the WP requires (mandatory diff).
- A documented scene complexity increase (e.g. teams-2 → teams-4 grew the
  visible plot count).
- A memory-leak fix that intentionally re-allocates per frame.

The justification must reference a `measureFixtureSvg` measurement delta
so the regression review can grep-verify the cause.

## Initial Baseline Creation

The first run of `pnpm --filter @razzoozle/web test visualRegression`
writes all 55 baselines and warns once per file:

```text
[visual-baseline] created initial baseline 2teams-stage-1__1366x768.json (hash=cbf29ce484222325)
```

After the initial commit, every subsequent run compares against the
committed baselines and fails on drift.

## Side-by-Side Composite

`pnpm --filter @razzoozle/web test visualOutput` runs the
`sideBySide.ts` generator that:

1. Renders each fixture twice — once with the pre-refactor "VORHER"
   parameters (`VORHER_STAGE_TO_HEIGHT`) and once with the current HEAD
   renderer.
2. Paints both onto a 1600 × N RGBA buffer (zero-dep encoder, no jsdom).
3. Writes the composite as `visual-output/side-by-side.png` (valid PNG,
   starts with the 8-byte PNG signature) and a per-fixture delta as
   `visual-output/side-by-side.report.json`.

The composite is for manual review — it is NOT a baseline.
